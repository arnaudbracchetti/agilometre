Leçon 0001 — Patterns de construction d'objets

Le pattern « named constructor »

Vous avez repéré ce code dans referentiel/domain/niveau.ts et posé la bonne question : pourquoi la validation ne vit-elle pas dans le constructeur ? 

export class Niveau {
  private constructor(readonly valeur: number) {}

  static creer(valeur: number): Niveau {
    if (valeur < Niveau.MIN || valeur > Niveau.MAX) {
      throw new NiveauInvalideError(valeur);
    }
    return new Niveau(valeur);
  }
}

Cette leçon répond à cette question — et à la question plus large qu'elle cache : qu'est-ce que ce pattern, pourquoi existe-t-il, et où est-ce que vous devez placer votre attention quand vous le voyez dans du code écrit par un agent.

Ce que fait le pattern

Un named constructor (aussi appelé static factory method) combine deux éléments :

  1. Un constructeur private — personne à l'extérieur de la classe ne peut écrire new Niveau(5).
  2. Une ou plusieurs méthodes statiques nommées (creer, reconstituer, vide…) qui, elles, ont le droit d'appeler ce constructeur privé — parce qu'en TypeScript, une méthode statique d'une classe peut toujours accéder au constructeur privé de cette même classe.

Mécanisme TypeScript exact : Static Methods Can Access Private Class Constructors In TypeScript — Ben Nadel.

Pourquoi ce détour, plutôt qu'un constructeur public ?

Trois raisons reviennent dans la littérature — retenez surtout la première, c'est celle qui a causé le bug :

  • Des noms qui expriment une intention. Niveau.creer(4) et Niveau.reconstituer(4) disent deux choses différentes : l'un valide une entrée fraîche, l'autre recharge une valeur déjà connue. new Niveau(4) ne dit rien de tout ça.
  • Empêcher un objet invalide d'exister. En interdisant new de l'extérieur, on force tout le monde à passer par un chemin contrôlé par la classe.
  • Réutilisation / sous-types / cache. Une factory peut retourner une instance mise en cache, ou une sous-classe — un constructeur ne le peut jamais. (Non pertinent pour Niveau, mais fait partie du pattern plus large.)

Source de référence sur ces trois bénéfices, dans un contexte Java mais transposable : Effective Java, Item 1 — résumé Baeldung.

La question qui a causé le bug : où valider ?

Le pattern répond à « comment nommer et contrôler la construction ». Il ne répond pas à « où doit vivre la validation d'un invariant ». Sur ce point précis, deux écoles valables existent — et le confondre avec la première question est ce qui a produit le bug.

Valider dans la factory

private constructor(v: number) {}

static creer(v: number) {
  if (invalide(v)) throw ...
  return new Niveau(v);
}

static reconstituer(v: number) {
  return new Niveau(v); // ⚠️ pas revalidé
}

Valider dans le constructeur

private constructor(v: number) {
  if (invalide(v)) throw ...
}

static creer(v: number) {
  return new Niveau(v); // validé
}

static reconstituer(v: number) {
  return new Niveau(v); // validé aussi
}

Tant qu'une classe n'a qu'une seule factory, les deux approches sont équivalentes. Le problème apparaît dès qu'une seconde factory arrive — ici reconstituer, ajoutée plus tard pour recharger un Niveau depuis la base de données. Si la validation vit dans creer, reconstituer ne la voit jamais : rien ne l'oblige à la rappeler, et le compilateur ne peut pas le détecter. C'est exactement ce qui s'est produit deux fois dans referentiel/domain/.

Ce qui a cassé La validation vivait dans Question.creer(). Question.reconstituer(), utilisée par le repository Prisma pour recharger une Question depuis la base, appelait directement le constructeur privé sans repasser par la validation — un chemin de construction entier échappait à l'invariant.

Deux écoles, un seul faux consensus

Il serait tentant de conclure « il faut toujours valider dans le constructeur ». Ce n'est pas ce que dit la littérature. Khalil Stemmler, référence TypeScript/DDD, défend explicitement l'inverse :

"When we use the new keyword, there's not really an elegant way to prevent a User from being created if certain validation rules don't pass." — il recommande de garder le constructeur "muet" et de faire vivre la validation dans la factory, qui retourne un Result<T> plutôt que de lever une exception.
— When to Use a Private Constructor — Khalil Stemmler

Sa raison : lever une exception depuis un constructeur oblige tout appelant à gérer un try/catch, même pour de la validation attendue et fréquente (un formulaire mal rempli, par exemple) — alors qu'un Result se traite comme une valeur normale.

Ce qu'il faut en retenir Les deux écoles sont défendables. Ce qui est indéfendable, c'est de choisir « valider dans la factory » sans se poser la question à chaque nouvelle factory ajoutée. Si vous gardez la validation hors du constructeur, la discipline à tenir est : chaque nouvelle factory doit soit rappeler explicitement la routine de validation, soit documenter pourquoi elle en est dispensée (ex: reconstituer charge des données déjà validées à l'import — un choix qui doit être écrit, pas silencieux).

Comment challenger l'agent la prochaine fois

Quand vous voyez ce pattern dans du code généré, trois questions suffisent :

  1. Combien de factories statiques cette classe a-t-elle ? (Cherchez tous les static qui appellent le constructeur privé.)
  2. La validation d'invariant est-elle dans le constructeur, ou dans une factory précise ?
  3. Si elle est dans une factory précise : est-ce que toutes les autres factories la rappellent, ou existe-t-il un chemin silencieux qui la contourne ?

Une question n'est pas claire, ou vous voulez creuser un exemple du projet ? Demandez à l'agent — c'est votre professeur ici, il peut réexpliquer, montrer d'autres classes du dépôt qui utilisent ce pattern, ou construire un contre-exemple.
